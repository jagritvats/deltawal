\section{Introduction}
\label{sec:intro}

Long-term memory for LLM agents is usually built by extracting facts from each conversation session with an LLM, embedding them, and retrieving the most similar facts when a question arrives~\citep{park2023generative,zhong2024memorybank,packer2023memgpt,chhikara2025mem0,xu2025amem,rasmussen2025zep}. Extraction costs one model call per session and takes seconds. A deployment that runs it on the write path makes the client wait; a deployment that moves it behind a message broker acknowledges the write immediately, but then the newest sessions are not yet in memory when the next question arrives. Benchmarks for conversational memory~\citep{maharana2024locomo,wu2025longmemeval} evaluate systems whose store is complete when the question is asked, so they do not see this window.

This paper studies two ways in which a fact-extraction memory returns the wrong value for a key that has changed. The first is \emph{read-after-write staleness}: the session containing an update has been acknowledged but not committed, and the reader answers from the superseded fact. In distributed-systems terms this violates read-your-writes~\citep{terry1994session}. The second is \emph{history erasure}: once the update is applied, the store or the read path keeps only the newest value, and questions about the earlier value (``what was my previous goal?'') become unanswerable. Erasure happens on the write side when a store updates a key in place, and on the read side when a retrieval step masks facts it believes superseded.

We make both failures measurable on LongMemEval-S~\citep{wu2025longmemeval}. A deterministic barrier holds the newest $\ell$ sessions in flight when a question fires, and a straggler model reorders commits with probability $p_\text{ooo}$. We then propose DeltaWAL, which treats the raw conversation as a write-ahead log~\citep{mohan1992aries}. Every session is written through to a Redis log with a monotonic epoch before the broker publish. At read time, one atomic call returns the committed watermark and the uncommitted log tail. Relevant uncommitted turns are merged with the stored facts in epoch order, and the reader is told that the higher epoch wins. DeltaWAL-Versioned adds an append-only store keyed by (entity key, source epoch), so no value is overwritten.

Our contributions are:
\begin{itemize}
\item A formulation of read-after-write staleness and history erasure for asynchronous fact-extraction memory, with a deterministic lag barrier and reordering model that make both reproducible without timing (Section~\ref{sec:system}).
\item DeltaWAL and DeltaWAL-Versioned: a write-through raw log with monotonic epochs, an atomic watermark-plus-tail snapshot, a relevance gate and an epoch-ordered merge that needs no extra model call, over an append-only store (Section~\ref{sec:systems}).
\item An evaluation on LongMemEval-S with three readers, every cell measured natively, together with latency on a real broker, log and vector store (Sections~\ref{sec:setup} and~\ref{sec:latency}).
\item History ablations showing that in-place overwrite and read-side masking both erase answers about earlier values, and that a compare-and-set fence prevents reordering corruption but not missed merges (Section~\ref{sec:history}).
\item External checks on non-update questions, on \memzero{} OSS with in-place updates, and on MemConflict with a blind two-rater audit of every evaluated question, including an exploratory negative result for epoch precedence on false corrections (Section~\ref{sec:external}).
\end{itemize}
