\section{Latency}
\label{sec:latency}

We measured latency apart from the accuracy runs, on the full stack (Redpanda, Redis, PostgreSQL with pgvector, local qwen3-embedding:0.6b) with \nm{tab6/config/questions} dev-split questions at lag \nm{tab6/config/lag}, with a real background worker that stops short of the last \nm{tab6/config/lag} sessions so that reads see a genuine in-flight tail (Table~\ref{tab:latency} in Appendix~\ref{app:tables}). We give medians with the 95th percentile in parentheses. B1 acknowledges only after extraction, embedding and upsert: \nm{tab6/B1_sync/write_ack/p50_ms}\,ms (\nm{tab6/B1_sync/write_ack/p95_ms}\,ms) with the local 12B extractor. The cloud extractor used for all evaluated sets took \nm{tab6/cloud_extractor_wall_s/median_s}\,s (\nm{tab6/cloud_extractor_wall_s/p95_s}\,s) per call, logged over \nm{tab6/cloud_extractor_wall_s/n} live calls during concurrent batch extraction, so seconds per session remain on this path either way. B2 acknowledges after the broker publish, \nm{tab6/B2_async/write_ack/p50_ms}\,ms (\nm{tab6/B2_async/write_ack/p95_ms}\,ms), and DeltaWAL after the WAL write-through and broker acknowledgement, \nm{tab6/DeltaWAL_warm/write_ack/p50_ms}\,ms (\nm{tab6/DeltaWAL_warm/write_ack/p95_ms}\,ms), so the WAL adds \nmdiff{tab6/DeltaWAL_warm/write_ack/p50_ms}{tab6/B2_async/write_ack/p50_ms}\,ms to the median. On the read path, excluding the query embedding, the warm DeltaWAL path takes \nm{tab6/DeltaWAL_warm/read_excl_query_embedding/p50_ms}\,ms (\nm{tab6/DeltaWAL_warm/read_excl_query_embedding/p95_ms}\,ms) against \nm{tab6/B1_sync/read_excl_query_embedding/p50_ms}\,ms (\nm{tab6/B1_sync/read_excl_query_embedding/p95_ms}\,ms) for B1's vector search; a cold read, before the background embedder has processed the tail, takes \nm{tab6/DeltaWAL_cold/read_excl_query_embedding/p50_ms}\,ms (\nm{tab6/DeltaWAL_cold/read_excl_query_embedding/p95_ms}\,ms); Lazy's query-time extraction takes \nm{tab6/Lazy/read_excl_query_embedding/p50_ms}\,ms (\nm{tab6/Lazy/read_excl_query_embedding/p95_ms}\,ms). These runs keep the log in memory only. In back-to-back runs on the same, more heavily loaded machine, making Redis fsync every WAL write raised DeltaWAL's write acknowledgement from \nm{latency_durable/nondurable_rerun/DeltaWAL/p50_ms}\,ms (\nm{latency_durable/nondurable_rerun/DeltaWAL/p95_ms}\,ms) to \nm{latency_durable/durable/DeltaWAL/p50_ms}\,ms (\nm{latency_durable/durable/DeltaWAL/p95_ms}\,ms), while B2's did not change: durability costs about \nm{latency_durable/deltawal_added_p50_ms}\,ms at the median. DeltaWAL-Versioned uses the same gate and merge and was not benchmarked separately, nor were B3 or the \memzero{} systems. These numbers come from one machine and indicate orders of magnitude.
