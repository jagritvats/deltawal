\section{Related Work}
\label{sec:related}

\paragraph{Memory for LLM agents.}
Agent memories range from experience logs with reflection~\citep{park2023generative} and forgetting-curve stores~\citep{zhong2024memorybank} to tiered paging~\citep{packer2023memgpt} and evolving linked notes~\citep{xu2025amem}. \memzero{} extracts facts and resolves them against existing memories with add, update and delete operations~\citep{chhikara2025mem0}; we show that its in-place update erases answers its own history table still holds. Zep's Graphiti engine is the closest design to ours on the history axis: it keeps a bi-temporal knowledge graph and invalidates superseded edges instead of deleting them, so earlier values remain queryable~\citep{rasmussen2025zep}. It does so with LLM extraction on the write path and leaves open the window between an acknowledged write and its indexing, which the raw WAL covers.

\paragraph{Freshness and write-path cost.}
\citet{omri2026agentmemory} characterise agent-memory workloads as systems workloads: memory construction shifts cost between the write and read paths, and when construction is slower than session arrival a system must block queries or serve stale memory, a freshness--latency trade-off they analyse for scheduling. We measure the accuracy side of that trade-off and give a read path that removes most of it. \citet{deng2026stale} locate personal-memory failures before generation, including stale values and missed merges; their keyed-update model commits revisions serially and atomically and keeps at most one active value per key for validity-restricted retrieval, with staleness arising from the age of background-published snapshots. Our setting differs in two ways: commits are asynchronous and can be reordered, so the newest write may be invisible rather than merely old, and we keep every version, since one active value erases the answers about earlier values.

\paragraph{Benchmarks.}
LoCoMo~\citep{maharana2024locomo} and LongMemEval~\citep{wu2025longmemeval} evaluate memory over long multi-session conversations with the full history available; we add a deterministic lag barrier and a reordering model on top of LongMemEval-S so that the same questions measure staleness. MemConflict~\citep{tao2026memconflict} generates dialogues in two stages, a session synopsis and then its realisation, and plants dynamic, static and conditional conflicts; we use its dynamic conflicts as a replication and its static ones to probe the limit of epoch precedence, after auditing every evaluated item. In the knowledge-conflict taxonomy of \citet{xu2024knowledge}, conflicts between retrieved memory items are inter-context conflicts, here with a known write order that epoch tags expose to the reader.

\paragraph{Systems foundations.}
Read-your-writes is one of the session guarantees for weakly consistent replicated storage~\citep{terry1994session}. Write-ahead logging makes a write durable before the derived state is updated~\citep{mohan1992aries}; DeltaWAL applies the idea to a store whose derived state is produced by an LLM. Per-user epochs are a single-writer instance of logical clocks~\citep{lamport1978time}, the pipeline follows the log-based broker design of Kafka~\citep{kreps2011kafka}, and the compare-and-set fence is a conditional upsert on a version number, as in optimistic concurrency control.
